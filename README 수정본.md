# [팀명] 급식 대기줄 실시간 확인 시스템

> 한 줄 소개: 학생들이 점심시간에 급식 대기 상황을 알 수 없는 불편을 YOLOv8n 기반 대기줄 분석과 웹사이트로 해결합니다.

## 1. 문제

**문제 한 문장:** 우리 학교 학생들은 점심시간에 급식실 대기줄을 미리 확인할 수 없어 식사하러 갈 시점을 정하기 어렵다.

**상황:**  
학생들은 급식실 앞에 줄이 길 것이라고 예상해 식사하러 가는 시간을 미루기도 한다. 그러다 급식실에 늦게 도착하면 식사할 시간이 부족해 여유롭게 밥을 먹기 어렵다.

**근거:**

- 나와 우리 반 친구 몇 명은 대기줄을 피하려고 주로 12시 35~45분쯤 급식실에 가며, 식사할 시간이 부족한 경험을 했다.
- 위 근거는 직접 경험하고 주변에서 확인한 사례이며, 학교 전체 학생을 대상으로 조사한 결과는 아니다.

## 2. 해결

**핵심 시나리오:**  
학생이 디벗으로 웹사이트 접속 → 시스템이 카메라 4대에 나뉘어 찍힌 대기줄을 YOLOv8n으로 분석 → 줄이 어느 카메라까지 이어졌는지로 혼잡도·예상 대기시간 계산 → 학생이 웹에서 혼잡도·예상 대기시간 확인 → 급식실로 이동할 시점 결정

**대기시간 판단 규칙:**

```text
배식대 ◀ [cam1] ◀ [cam2] ◀ [cam3] ◀ [cam4]   (줄이 뒤로 길어지는 방향)
```

| 줄이 이어진 카메라 | 혼잡도 | 예상 대기시간 |
| --- | --- | --- |
| cam1에도 줄 없음 | 매우 여유 | 0~3분 |
| cam1 | 여유 | 약 5분 |
| cam1 + cam2 | 보통 | 약 10분 |
| cam1 + cam2 + cam3 | 혼잡 | 약 15분 |
| cam1 ~ cam4 모두 | 매우 혼잡 | 20분 초과 |

※ cam1부터 **이어서** 줄이 있는 카메라 수로 판단한다. cam1이 비어 있는데 cam3에만 사람이 있으면 지나가는 사람으로 보고 '매우 여유'로 판단한다.

| 구분 | 기능 |
| --- | --- |
| 필수 (15:30까지 반드시) | ① 영상 속 지정된 대기 구역의 사람 수 탐지 ② 줄이 이어진 위치를 반영한 예상 대기시간 계산 ③ 웹사이트에 혼잡도·예상 대기시간 표시 |
| 선택 (시간이 남으면) | 일정 간격 자동 갱신, 혼잡도를 색상으로 표시, 마지막 갱신 시각 표시 → **모두 구현** (1초마다 갱신, 5단계 색상, 갱신 시각 표시) |
| 추가 구현 | 지나가는 사람 걸러내기(머문 시간·비율·단계 변화 지연), CCTV 설치 각도에 따른 판단 기준 선택, 카메라 연결이 끊기면 'OFF' 표시 |
| 제외 (오늘 하지 않음) | 개인 식별 및 이동 경로 저장, 급식 예약, 개인별 알림 |

**완성 여부 (15:30 기준)**

- [ ] 영상 속 대기 인원 탐지
- [ ] 예상 대기시간 계산
- [ ] 웹사이트에서 혼잡도·예상 대기시간 확인

※ 시연에서 직접 확인한 항목만 체크한다.

## 3. 설계

**화면 흐름:**  
웹사이트 접속 → 신호등(혼잡도·예상 대기시간) 확인 → 마지막 갱신 시각 확인

※ 한 페이지에서 한눈에 확인하도록 구성했다.  
※ 개인정보 보호를 위해 **웹사이트에는 카메라 영상과 구역별 인원을 보내지 않고 혼잡도와 예상 대기시간만 표시**한다. 영상과 구역별 인원은 분석용 컴퓨터 화면에서만 볼 수 있다.

**전체 구조:**

```text
카메라 4대 ──▶ queue_monitor.py ──▶ status.json ──▶ web_server.py ──▶ 디벗 웹브라우저
              (YOLOv8n 사람 탐지·      (1초마다 저장,       (Flask,
               구역 판단·혼잡도 계산)    숫자만 저장)         1초마다 읽어 표시)
```

**데이터 구조:**

```text
대기 구역 (cameras.json):  카메라 이름(cam1~cam4), 영상 번호/주소, 영상 내 구역 좌표, 판단 기준(발/몸 가운데/겹침)
판단 설정 (cameras.json):  인식 최소 점수, 줄로 인정할 최소 인원, 머문 시간 기준, 판단 시간 범위, 단계 변경 대기 시간
분석 결과 (status.json):   분석 시각, 혼잡도, 예상 대기시간, 줄이 이어진 카메라 수, 카메라별 대기 인원·줄 여부
표시 정보 (웹):            혼잡도 색상, 예상 대기시간, 마지막 갱신 시각, 연결 상태(OFF)
```

**기술 선택:**

- **선택:** YOLOv8n으로 영상 속 사람을 탐지하고, 미리 지정한 대기 구역 안의 사람만 집계한다. Python과 OpenCV로 영상을 처리하고, Flask와 HTML·CSS·JavaScript로 결과를 보여 주는 웹사이트를 구현했다.
- **대기시간 계산:** 줄을 따라 카메라 4대를 두고, **줄이 어느 카메라까지 이어졌는지**로 혼잡도와 예상 대기시간을 정한다.
- **지나가는 사람 걸러내기 (3중 장치):**
  1. 사람마다 번호를 붙여 추적(ByteTrack)하고, 구역 안에 **3초 이상 머문 사람만** 줄 선 사람으로 센다.
  2. 최근 **10초 중 60% 이상** 줄이 있어야 그 카메라에 줄이 있다고 판단한다.
  3. 새 혼잡도가 **5초 이상 유지**돼야 바뀌고, **한 번에 한 단계씩만** 바뀐다.
- **CCTV 설치 각도 대응:** 카메라마다 판단 기준을 고를 수 있다. 비스듬히 찍으면 발 위치(`bottom`), CCTV처럼 높이 달려 발이 안 보이면 몸 가운데(`center`), 바로 위에서 내려다보면 몸이 구역과 겹친 비율(`overlap`)을 쓴다.
- **고르지 않은 안과 이유:** `대기 인원 ÷ 분당 평균 배식 인원`으로 대기시간을 계산하는 방식은 줄이 길어지면 사람이 겹쳐 인원 수가 부정확해지므로 사용하지 않는다. 학생이 직접 대기 인원을 입력하는 방식은 지속적인 참여가 필요하다. 얼굴 인식은 인원 집계에 필요하지 않아 사용하지 않는다. 추적 번호는 화면 속 순간적인 번호일 뿐 누구인지 알아내지 않으며 저장하지도 않는다.
- **막히면:** CCTV 연결이 어려우면 사용 허가를 받은 테스트 영상이나 웹캠 1대를 4구역으로 나눠 시연한다. 테스트 영상이나 예시 데이터를 사용할 경우 화면에 표시한다.

## 4. 실행 링크·실행 방법

- **실행 링크:** 같은 와이파이에서 `http://[분석 컴퓨터 IP]:5000` (IP는 `ipconfig`로 확인)
- **사용 기기:** 디벗 또는 웹브라우저가 있는 컴퓨터
- **시연 데이터:** [실제 사용한 테스트 영상 또는 웹캠 시연 방식 설명 입력]

**실행 방법 (Windows, Python 3.12):**

```bash
# 1. 설치 (처음 한 번)
py -3.12 -m pip install ultralytics opencv-python flask

# 2. 카메라별 대기 구역 그리기 (처음 한 번, cam1이 배식대에 가장 가까운 구역)
py -3.12 queue_monitor.py --set-roi cam1
py -3.12 queue_monitor.py --set-roi cam2
py -3.12 queue_monitor.py --set-roi cam3
py -3.12 queue_monitor.py --set-roi cam4

# 3. 분석 실행 (명령 창 1)
py -3.12 queue_monitor.py

# 4. 웹사이트 실행 (명령 창 2)
py -3.12 web_server.py
```

- 구역 그리기: 마우스 왼쪽 클릭으로 꼭짓점 추가, 오른쪽 클릭으로 취소, Enter로 저장
- 카메라 번호와 판단 기준은 `cameras.json`에서 바꾼다. (처음 실행할 때 자동 생성, 웹캠 1대 연습 모드가 기본값)
- `lap` 관련 오류가 나면 `py -3.12 -m pip install lapx`

**파일 구성:**

| 파일 | 역할 |
| --- | --- |
| `queue_monitor.py` | 카메라 영상 분석, 대기 구역 판단, 혼잡도 계산, `status.json` 저장 |
| `web_server.py` | `status.json`을 읽어 웹사이트로 표시 |
| `cameras.json` | 카메라·대기 구역·판단 기준 설정 (자동 생성) |
| `status.json` | 1초마다 갱신되는 분석 결과 (자동 생성) |
| `yolov8n.pt` | YOLOv8n 모델 (처음 실행할 때 자동 다운로드) |

**AI 결과에서 직접 고친 부분:**

- 처음 결과는 카메라 1대로 인원 수를 세어 `인원 ÷ 배식 속도`로 대기시간을 계산했다. 실제 급식실 줄은 길고 사람이 겹치므로, 줄이 어느 카메라까지 이어졌는지로 판단하는 규칙을 직접 정해 바꿨다.
- 처음 결과는 발 위치로만 판단했다. 학교 CCTV는 높은 곳에 있어 발이 안 보일 수 있다는 점을 발견해, 설치 각도에 맞는 판단 기준을 고를 수 있게 바꿨다.
- 처음 결과는 한 명만 지나가도 혼잡도가 바뀔 수 있었다. 이 문제를 직접 찾아 머문 시간과 단계 변경 지연을 추가했다.
- 처음 기획은 웹사이트에 영상을 보여 주는 것이었으나, 개인정보 보호를 위해 영상을 빼고, 학생에게 필요한 정보만 남기도록 구역별 인원도 빼서 혼잡도와 예상 대기시간만 보여 주도록 바꿨다.

## 8. 한계와 다음 계획

**한계:**

- 실제 급식실 CCTV에는 아직 연결하지 않았고, 웹캠·테스트 영상으로만 확인했다.
- 사람이 많이 겹치거나 줄이 촬영 범위를 벗어나면 대기 인원이 실제와 다르게 계산될 수 있다.
- 구역별 예상 대기시간(5·10·15·20분)은 직접 정한 값으로, 메뉴와 운영 상황에 따라 실제와 다를 수 있다.
- 지나가는 사람을 걸러내는 장치 때문에 혼잡도가 실제보다 몇 초~수십 초 늦게 바뀐다.
- 위에서 바로 내려다보는 CCTV에서는 YOLOv8n의 사람 탐지 정확도가 떨어질 수 있다.
- 디벗이 분석 컴퓨터와 같은 와이파이에 있어야 접속할 수 있다.
- 실제 CCTV 활용과 학생용 화면 제공은 학교와 협의가 필요하다.

**다음 계획:**

1. 실제 급식실에서 직접 센 인원과 프로그램 결과를 비교해 대기 구역, 머문 시간, 최소 인원 기준을 조정한다.
2. 실제 대기시간을 측정해 구역별 예상 대기시간 값을 고친다.
3. Oracle Cloud Infrastructure(OCI)에 웹사이트를 호스팅해 항상 열어 두고, 학교 밖 와이파이에서도 접속할 수 있도록 한다.
4. 디벗에서 화면 가독성을 점검한다.
